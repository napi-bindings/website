3b:T3caf,<h1 id="the-quickjs-napi-executable">The <code>quickjs-napi</code> executable</h1>
<p><code>quickjs-napi</code> is a small Node.js-like runtime built on the library. It runs
CommonJS scripts, loads <code>.node</code> addons with <code>require</code>, and provides the subset
of Node.js that addon packages and their tests need. It is also the reference
embedder of the library (<a href="/projects/quickjs-napi/docs/embedding/">embedding.md</a>).</p>
<p>Sources: <code>host/main.c</code> (command line, event loop, natives),
<code>host/bootstrap.js</code> (module loader, <code>process</code>, builtin modules; embedded in
the executable at build time by <code>cmake/embed.cmake</code>) and <code>host/spawn.c</code>
(child processes).</p>

<h2 id="modules"><a class="heading-anchor" href="#modules">Modules</a></h2>
<p>The script runs as a <strong>CommonJS module</strong>: <code>require</code>, <code>module</code>, <code>exports</code>,
<code>__filename</code> and <code>__dirname</code> are defined as in Node.js.</p>
<p><code>require(id)</code> resolves like Node.js for what addon packages use:</p>
<ol>
<li>builtin modules (<code>require('buffer')</code>, ...);</li>
<li>relative (<code>./</code>, <code>../</code>) and absolute paths, trying the exact name, then
the extensions <code>.js</code>, <code>.json</code>, <code>.node</code>;</li>
<li>directories: <code>package.json</code> <code>"main"</code>, then <code>index.js</code>, <code>index.json</code>,
<code>index.node</code>;</li>
<li><code>node_modules</code> directories, from the requiring module's directory up to the
root.</li>
</ol>

<h3 id="child_process"><a class="heading-anchor" href="#child_process"><code>child_process</code></a></h3>
<p>Children are started directly, <strong>without a shell</strong>, with libuv's <code>uv_spawn</code>
(<code>host/spawn.c</code>):</p>
<ul>
<li><code>spawnSync(file, args, options)</code> runs the child on a private libuv loop
until it exits and its pipes are drained. Options: <code>env</code>, <code>cwd</code>, <code>stdio</code>
(<code>'pipe'</code>, <code>'inherit'</code>, <code>'ignore'</code>), <code>input</code>, <code>encoding</code>, <code>timeout</code> (the
child is killed with <code>killSignal</code>, <code>SIGTERM</code> by default, and <code>error.code</code> is
<code>ETIMEDOUT</code>). The result has <code>pid</code>, <code>status</code>, <code>signal</code>, <code>stdout</code>, <code>stderr</code>,
<code>output</code> and <code>error</code> (<code>ENOENT</code> when the program does not exist).</li>
<li><code>spawn(file, args, options)</code> runs the child on the main loop and returns a
<code>ChildProcess</code>-like emitter: <code>stdout</code>/<code>stderr</code> streams with <code>data</code> events
and <code>setEncoding</code>, then <code>exit</code> and <code>close</code> events, <code>kill(signal)</code>, and an
<code>error</code> event when it cannot start. An asynchronous child's stdin is never a
pipe: it reads end-of-file.</li>
</ul>
<p>Every child of the test suites is the same executable (<code>process.execPath</code>), so
the tests that spawn processes run on every platform.</p>
<h2 id="event-loop"><a class="heading-anchor" href="#event-loop">Event loop</a></h2>
<p>The executable runs the host's libuv loop (<code>uv_run</code>) until nothing referenced
is left, then emits <code>beforeExit</code> (whose listeners may schedule more work, in
which case the loop runs again), then <code>exit</code>.</p>

callback from the loop) a <strong>checkpoint</strong> runs: the promise jobs and
<code>process.nextTick</code> callbacks, then the unhandled rejections, repeated until
both are empty. The same function is installed as the library's checkpoint
(<code>qjsnapi_host_set_checkpoint</code>), so Node-API callbacks behave like Node.js
macrotasks.</p>
<h2 id="errors-and-exit"><a class="heading-anchor" href="#errors-and-exit">Errors and exit</a></h2>
<ul>
<li>An exception that no frame catches (thrown by a timer, a microtask, a
Node-API finalizer or callback) goes to <code>process.on('uncaughtException')</code>
listeners; without listeners the error is printed and the process exits
with code <strong>1</strong>.</li>
<li>An unhandled promise rejection goes to <code>process.on('unhandledRejection')</code>;
without listeners it is treated as an uncaught exception (Node.js default
<code>--unhandled-rejections=throw</code>).</li>
<li>At the normal end of the script, <code>beforeExit</code> and <code>exit</code> are emitted and the
host is <strong>destroyed</strong>: cleanup hooks, then finalizers
(<a href="/projects/quickjs-napi/docs/architecture/#teardown">architecture.md</a>). The exit code is
<code>process.exitCode</code> (0 by default).</li>
<li><code>process.exit(code)</code> and fatal exceptions end the process <strong>immediately</strong>,
like Node.js: <code>exit</code> is emitted, the thread pool is shut down, and no
cleanup hook or finalizer runs, nor is in-flight work waited for.</li>
<li><code>napi_fatal_error</code> prints <code>FATAL ERROR: &#x3C;location> &#x3C;message></code> and aborts
(<code>_exit(134)</code> on Windows).</li>
<li>On Windows, stdout and stderr are in binary mode: <code>\n</code> is written as is,
as Node.js does, so a parent reading the pipe sees the same bytes on every
platform.</li>
</ul>
