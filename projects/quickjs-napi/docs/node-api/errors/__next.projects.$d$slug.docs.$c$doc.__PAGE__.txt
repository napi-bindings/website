<h2 id="pending-exceptions"><a class="heading-anchor" href="#pending-exceptions">Pending exceptions</a></h2>
<p>QuickJS keeps at most <strong>one pending exception</strong> on the runtime, and
quickjs-napi uses it directly:</p>
<ul>
<li>a failed call into JavaScript leaves the exception pending and returns
<code>napi_pending_exception</code>;</li>
<li><code>napi_throw*</code> make an exception pending and return <code>napi_ok</code>;</li>
<li>while an exception is pending, <a href="/projects/quickjs-napi/docs/node-api/#functions-that-run-javascript">functions that run JavaScript</a>
refuse to start, but value creation and the functions on this page still
work;</li>
<li>when the native callback returns, a pending exception propagates to the
JavaScript caller. With no JavaScript caller (finalizers, async work,
thread-safe functions) it is reported as uncaught.</li>
</ul>
<p>A typical error path:</p>
<pre class="shiki shiki-themes github-light github-dark" style="background-color:#fff;--shiki-dark-bg:#24292e;color:#24292e;--shiki-dark:#e1e4e8" tabindex="0"><code><span class="line"><span style="color:#24292E;--shiki-dark:#E1E4E8">napi_value result;</span></span>

<h2 id="error-objects"><a class="heading-anchor" href="#error-objects">Error objects</a></h2>
<p>The four error constructors (<code>Error</code>, <code>TypeError</code>, <code>RangeError</code>,
<code>SyntaxError</code>) are captured when the host is created, so replacing
<code>globalThis.Error</code> later does not change what these functions create. Like
Node.js, they create <code>new Ctor(message)</code> and, when a code is given, set an
own enumerable <code>code</code> property after construction.</p>
<hr>
<h2 id="create-an-error-object"><a class="heading-anchor" href="#create-an-error-object">Create an error object</a></h2>
<p>These functions only create the object; nothing is thrown. They work while an
exception is pending.</p>
