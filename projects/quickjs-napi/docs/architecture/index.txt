<h2 id="goals-and-constraints"><a class="heading-anchor" href="#goals-and-constraints">Goals and constraints</a></h2>
<p>quickjs-napi implements Node-API (version 10) on top of the
<a href="https://bellard.org/quickjs/" target="_blank" rel="noreferrer noopener">QuickJS</a> engine, so that addons compiled for
Node.js load <strong>unchanged</strong>. Everything in the design follows from that goal:</p>
<ol>
<li><strong>Binary compatibility.</strong> An addon built by node-gyp, node-addon-api or
napi-rs does not link against any quickjs-napi library: it resolves the
<code>napi_*</code> (and <code>uv_*</code>) symbols from the running process, exactly as it does
from <code>node</code>. The executable must therefore export the whole Node-API and
libuv.</li>
<li><strong>Observable Node.js semantics.</strong> The reference is Node.js <strong>22.23.4</strong>
(<code>src/js_native_api_v8.cc</code>, <code>src/node_api.cc</code>). Status codes, pending
exceptions, property order, error messages and finalizer timing follow it.
Each difference is a documented deviation (see
<a href="/projects/quickjs-napi/docs/compatibility/">compatibility.md</a>).</li>
<li><strong>QuickJS as it is.</strong> The engine is used through its public C API
(<code>quickjs.h</code>); it is not patched. When QuickJS lacks something V8 has (weak
callbacks, <code>new.target</code> in C functions, a class ID enum, DataView
accessors), the library builds it from what QuickJS has.</li>
</ol>
<p>The main difference between the two engines is the memory model: <strong>V8 uses a
tracing GC</strong>, so an object stays alive until a collection finds it unreachable.
<strong>QuickJS uses reference counting</strong> plus a cycle collector, so an object is
freed as soon as its last reference goes away. Much of the lifetime machinery
below exists to make reference counting look like a tracing GC to addons.</p>

<h2 id="host-and-env"><a class="heading-anchor" href="#host-and-env">Host and env</a></h2>
<p>Node.js has one <em>environment</em> per thread and one <code>napi_env</code> per loaded addon.
quickjs-napi keeps the same split:</p>
<pre class="mermaid">classDiagram

<ul>
<li><strong><code>qjsnapi_host</code></strong> (one per <code>JSContext</code>, stored as the context opaque) owns
everything that is shared: the libuv loop, the captured builtins, the
<code>WeakMap</code> of lifetime holders, the list of envs and loaded modules, the
<em>kept objects</em> list, and the embedder's callbacks (uncaught exception
handler, checkpoint).</li>
<li><strong><code>napi_env__</code></strong> (one per addon initialization) owns what Node.js keeps per
module: the <strong>module API version</strong> (which changes some behaviours, e.g.
<code>napi_cannot_run_js</code> instead of <code>napi_pending_exception</code> during teardown),
the last error, the handle-scope arena, cleanup hooks, references, the
finalizer queue, and the async objects not yet released.</li>
</ul>
<p>Loading the same addon twice creates two envs, like <code>process.dlopen</code> in
Node.js: the initializer runs again and returns new exports.</p>
<h2 id="values-and-handle-scopes"><a class="heading-anchor" href="#values-and-handle-scopes">Values and handle scopes</a></h2>
<p>A <code>napi_value</code> is an opaque pointer. In quickjs-napi it <strong>points to a
<code>JSValue</code> slot</strong> in an arena owned by the env. Each slot owns exactly one
QuickJS reference (<code>JS_DupValue</code> when the slot is filled, <code>JS_FreeValue</code> when
its scope closes). This is the reference-counting equivalent of a V8 local
handle.</p>
<pre class="mermaid">flowchart LR
    subgraph arena["env arena: chunks of 256 JSValue slots, never moved"]
        direction LR
        c1["chunk 1&#x3C;br/>slots 0..255"] --- c2["chunk 2&#x3C;br/>slots 0..255"] --- c3["chunk 3&#x3C;br/>..."]
    end
    root["root scope&#x3C;br/>mark: chunk 1, slot 0"] -.-> c1
    s1["implicit scope of a call&#x3C;br/>mark: chunk 1, slot 17"] -.-> c1
    s2["napi_open_handle_scope&#x3C;br/>mark: chunk 2, slot 40"] -.-> c2
    top["top: next free slot"] -.-> c3
</pre>
<ul>
<li>Slots are allocated by bumping <code>arena.top</code>. Chunks are linked, never
reallocated, so a <code>napi_value</code> stays valid until its scope closes.</li>
<li>A scope records the arena position (<code>qn_mark</code>) when it opens. Closing it
frees, in LIFO order, every slot allocated since then and resets <code>top</code>.
Closing a scope is O(number of values created in it), with no per-handle
bookkeeping.</li>
<li><strong>Escapable scopes</strong> reserve one slot in the parent <em>before</em> recording their
own mark. <code>napi_escape_handle</code> stores a duplicated reference into that slot,
so the value survives the inner scope. Escaping twice returns
<code>napi_escape_called_twice</code>.</li>
<li>Every native entry point (a function call, a finalizer, module init, a loop
callback) runs inside an <strong>implicit scope</strong>, so addons that never open scopes
do not leak. Closing a scope that is not the innermost one returns
<code>napi_handle_scope_mismatch</code>.</li>
<li>Scope records are recycled through a free list, so opening a scope does not
allocate in the steady state.</li>
</ul>
<h2 id="calling-native-functions"><a class="heading-anchor" href="#calling-native-functions">Calling native functions</a></h2>
<p><code>JS_NewCFunctionData</code> is not enough for Node-API: its trampoline does not expose
<code>new.target</code>, which <code>napi_get_new_target</code> and <code>napi_define_class</code> need. Native
functions are therefore objects of a dedicated QuickJS class with a <code>call</code>
hook. QuickJS passes <code>JS_CALL_FLAG_CONSTRUCTOR</code> and, for construct calls,
<code>new.target</code> as <code>this_val</code>.</p>
<pre class="mermaid">sequenceDiagram
    participant JS as JavaScript
    participant T as qn_function_call (trampoline)
    participant S as handle-scope arena
    participant CB as addon callback
    JS->>T: f(a, b) or new F(a, b)
    alt construct call
        T->>T: receiver = object with new.target.prototype
    else plain call
        T->>T: receiver = this
    end
    T->>S: open implicit scope
    T->>T: clear last error, native_depth++
    T->>CB: cb(env, &#x26;callback_info)
    CB->>S: napi_create_* (new slots)
    CB-->>T: napi_value result (or NULL)
    T->>T: native_depth--
    alt exception pending
        T-->>JS: JS_EXCEPTION (the exception propagates)
    else
        T->>T: duplicate the result out of the scope
    end
    T->>S: close the scope (frees every slot of the call)
    T-->>JS: result, or the receiver when a construct call&#x3C;br/>returned a non-object
</pre>
<ul>
<li><code>napi_callback_info</code> points to a stack record (<code>this</code>, <code>new.target</code>,
<code>argc</code>, <code>argv</code>, <code>data</code>): there is no allocation per call.</li>
<li>The per-function record (<code>qn_function</code>: env, callback, data) is owned by the
function object and freed by its class finalizer. It holds no <code>JSValue</code>, so
the class needs no <code>gc_mark</code> hook.</li>
<li><code>host->native_depth</code> counts the native frames on the stack. It is <code>0</code> only
when no JavaScript is below the running native code, which is how callback
scopes decide whether to run a microtask checkpoint.</li>
<li>A function whose env is shutting down throws an <code>InternalError</code> instead of
calling into the addon.</li>
</ul>
<p><code>napi_define_class</code> creates such a function and defines the instance
properties on its <code>prototype</code> and the static ones on the constructor. As with
V8's prototype templates, a later instance property with the same key replaces
an earlier one regardless of its attributes.</p>
<h2 id="errors-and-exceptions"><a class="heading-anchor" href="#errors-and-exceptions">Errors and exceptions</a></h2>
<p>Node-API reports errors in two ways, and quickjs-napi keeps both exactly like
Node.js:</p>
<ol>
<li><strong>Status codes.</strong> Every function returns a <code>napi_status</code> and records it as
the env's <em>last error</em> (<code>napi_get_last_error_info</code>). The checks are the
macros of <code>qjsnapi_internal.h</code>, named after their Node.js equivalents:
<code>CHECK_ENV</code>, <code>CHECK_ARG</code>, <code>RETURN_STATUS_IF_FALSE</code>, <code>NAPI_PREAMBLE</code>,
<code>CHECK_JS</code>, <code>GET_RETURN_STATUS</code>.</li>
<li><strong>JavaScript exceptions.</strong> QuickJS keeps the pending exception on the
runtime. A JavaScript failure leaves it pending, exactly like V8, and the
function returns <code>napi_pending_exception</code>.</li>
</ol>
<pre class="mermaid">flowchart TD
    A["API that may run JavaScript"] --> P{"NAPI_PREAMBLE"}
    P -- "env is NULL" --> E1["napi_invalid_arg"]
    P -- "an exception is already pending" --> E2["napi_pending_exception"]
    P -- "env is tearing down" --> E3["napi_cannot_run_js (module API >= 10)&#x3C;br/>napi_pending_exception (older modules)"]
    P -- ok --> B["clear the last error, run the QuickJS call"]
    B -- "JavaScript threw" --> E4["napi_pending_exception&#x3C;br/>(the exception stays pending)"]
    B -- "other failure" --> E5["specific status&#x3C;br/>(napi_*_expected, napi_generic_failure, ...)"]
    B -- ok --> OK["napi_ok"]
</pre>
<p>When a native callback returns with an exception pending, the trampoline
returns <code>JS_EXCEPTION</code>, so the exception propagates to the JavaScript caller.
When there is no JavaScript caller (a finalizer, an async work completion, a
thread-safe function call), the exception goes to the host's <strong>uncaught
handler</strong> (<code>qjsnapi_host_set_uncaught_handler</code>), which the executable maps to
<code>process.on('uncaughtException')</code>.</p>
<h2 id="object-lifetime"><a class="heading-anchor" href="#object-lifetime">Object lifetime</a></h2>
<p>This is where the two engines differ most. The
<a href="/projects/quickjs-napi/docs/node-api/lifetime/">lifetime reference</a> describes the API; this section
explains the mechanism.</p>
<h3 id="references"><a class="heading-anchor" href="#references">References</a></h3>
<p><code>napi_ref</code> (<code>struct napi_ref__</code>) mirrors <code>v8impl::Reference</code>:</p>
<pre class="mermaid">stateDiagram-v2
    [*] --> Strong: create with count > 0
    [*] --> Weak: create with count 0&#x3C;br/>(object, function, local symbol)
    [*] --> Empty: create with count 0&#x3C;br/>(any other value)
    Strong --> Weak: unref reaches 0, weakable target
    Strong --> Empty: unref reaches 0, other value
    Weak --> Strong: ref, target still alive
    Weak --> Empty: target collected (holder finalizer)
    Strong --> [*]: napi_delete_reference
    Weak --> [*]: napi_delete_reference
    Empty --> [*]: napi_delete_reference
</pre>
<ul>
<li><strong>Strong</strong> (count > 0): the reference owns a <code>JSValue</code>.</li>
<li><strong>Weak</strong> (count 0; object, function or non-registered symbol): it holds a
JavaScript <code>WeakRef</code>. QuickJS reports a <code>WeakRef</code> target dead as soon as its
refcount drops to zero, so <code>napi_get_reference_value</code> returns <code>NULL</code> exactly
when the value is gone. The target is also on the <em>kept-objects</em> list until
the next clear (see below).</li>
<li><strong>Empty</strong> (count 0, any other value): the value is released for good, like a
reset V8 persistent.</li>
<li>Registered symbols (<code>Symbol.for</code>) cannot be held weakly by QuickJS. They are
never collected anyway, so they stay strong (<code>keep_strong</code>), which is what
Node.js observably does.</li>
</ul>
<h3 id="kept-objects"><a class="heading-anchor" href="#kept-objects">Kept objects</a></h3>
<p>V8 keeps the target of a weak handle alive until the next GC. node-addon-api
relies on this: <code>Napi::Weak(Object::New(env))</code> is used later in the same
synchronous code. Under reference counting such an object would die when the
call's scope closes. So when a reference becomes weak, its target is also put
on a <strong>kept-objects list</strong>, like the <code>[[KeptAlive]]</code> list of ECMAScript
<code>WeakRef</code>s. The list is cleared:</p>
<ul>
<li>at the end of every macrotask (the library's checkpoint, after each callback
from the event loop);</li>
<li>by <code>gc()</code> in the executable;</li>
<li>by the embedder, with <code>qjsnapi_host_clear_kept_objects</code>;</li>
<li>at teardown.</li>
</ul>
<h3 id="weak-callbacks-through-holders"><a class="heading-anchor" href="#weak-callbacks-through-holders">Weak callbacks through holders</a></h3>
<p>V8 notifies a weak persistent when its target is collected; QuickJS has no
such hook in its C API. quickjs-napi gets the notification through a
<strong>holder</strong>:</p>
<pre class="mermaid">sequenceDiagram
    participant A as addon
    participant L as lifetime.c
    participant W as host.holders (WeakMap)
    participant H as NapiHolder object
    participant G as QuickJS GC
    participant Q as env.pending_finalizers
    participant U as event loop (uv_check)
    A->>L: napi_wrap / napi_create_reference / napi_type_tag_object
    L->>W: get(target), or set(target, new holder)
    L->>H: register the reference, wrap or tag
    Note over G: the target becomes unreachable
    G->>W: JS_RunGC drops the entry of the dead key
    W->>H: the holder is freed
    H->>L: class finalizer: notify every registered reference
    L->>Q: no finalizer: reset now&#x3C;br/>with a finalizer: queue it
    U->>Q: qjsnapi_host_run_finalizers
    Q->>A: finalize_cb(env, data, hint) in its own scope
</pre>
<ul>
<li>Each target of a reference, wrap or type tag gets <strong>one holder</strong>, an object
of the internal <code>NapiHolder</code> class stored in <code>host->holders</code>, a <code>WeakMap</code>
keyed by the target.</li>
<li>QuickJS drops the entries of dead keys during <code>JS_RunGC</code>. The holder is
freed, and its class finalizer plays the role of V8's weak callback.</li>
<li>The holder also stores the <code>napi_wrap</code> reference and the type tag, so
<strong>wrapping and tagging work on any object</strong> (frozen objects, proxies,
functions) without adding properties to it.</li>
<li>QuickJS drops weak entries <em>before</em> collecting cycles, so a target that died
in a cycle is only seen dead by a second pass: <code>gc()</code> runs <code>JS_RunGC</code> twice.</li>
</ul>
<h3 id="finalizers-are-deferred"><a class="heading-anchor" href="#finalizers-are-deferred">Finalizers are deferred</a></h3>
<p>Finalizers <strong>never run inside the GC</strong>. As in Node.js, they are queued on the
env (<code>pending_finalizers</code>) and run later from the event loop, where
JavaScript may run (<code>qjsnapi_host_run_finalizers</code>), each in its own handle
scope and followed by a checkpoint. Finalizers still queued at teardown run
then, with JavaScript disabled (<code>napi_cannot_run_js</code>).</p>
<p>External values (<code>napi_create_external</code>), external ArrayBuffers and external
Buffers use the same queue: their finalizer runs after the object is
collected, never synchronously.</p>
<h2 id="the-event-loop"><a class="heading-anchor" href="#the-event-loop">The event loop</a></h2>
<p>The host is bound to a <strong>libuv loop</strong>: <code>qjsnapi_host_create</code> creates its own,
<code>qjsnapi_host_create_with_loop</code> uses the embedder's. The library only adds
handles to the loop; <strong>the embedder runs it</strong> (<code>uv_run</code>).</p>
<pre class="mermaid">flowchart LR
    subgraph iteration["one libuv iteration"]
        direction LR
        T["timers"] --> P["pending"] --> I["idle / prepare"] --> PO["poll (I/O)"] --> C["check"] --> CL["close callbacks"]
    end
    W["async work completion&#x3C;br/>(uv_queue_work after_work)"] -.-> PO
    TS["thread-safe function dispatch&#x3C;br/>(uv_async_t)"] -.-> PO
    FI["finalizer_idle (uv_idle_t)&#x3C;br/>active while finalizers are queued,&#x3C;br/>so poll does not block"] -.-> I
    FC["finalizer_check (uv_check_t, unreferenced)&#x3C;br/>runs the queued finalizers"] -.-> C
</pre>
<table>
<thead>
<tr>
<th>Handle</th>
<th>Owner</th>
<th>Purpose</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>finalizer_check</code> (<code>uv_check_t</code>, unreferenced)</td>
<td><code>loop.c</code></td>
<td>runs the queued finalizers at the end of each iteration, then a checkpoint</td>
</tr>
<tr>
<td><code>finalizer_idle</code> (<code>uv_idle_t</code>)</td>
<td><code>loop.c</code></td>
<td>active only while finalizers are queued: keeps the loop alive and stops the poll phase from blocking (Node.js uses a referenced <code>SetImmediate</code>)</td>
</tr>
<tr>
<td><code>uv_work_t</code> per queued work item</td>
<td><code>async.c</code></td>
<td><code>execute</code> on the thread pool, <code>complete</code> on the loop thread</td>
</tr>
<tr>
<td><code>uv_async_t</code> per thread-safe function</td>
<td><code>tsfn.c</code></td>
<td>wakes the loop thread to dispatch queued calls (referenced unless <code>napi_unref_threadsafe_function</code>)</td>
</tr>
</tbody>
</table>
<p>Every callback from the loop into native code goes through a <strong>callback
frame</strong> (<code>qn_callback_enter</code> / <code>qn_callback_leave</code>): a handle scope, a callback
scope, and on exit an exception check (reported as uncaught) and, for the
outermost scope, a <strong>checkpoint</strong>. The default checkpoint runs the pending
promise jobs (<code>JS_ExecutePendingJob</code>); the embedder can replace it
(<code>qjsnapi_host_set_checkpoint</code>) to drain its own queues too, which is what the
executable does for <code>process.nextTick</code> and unhandled rejections.</p>
<h3 id="async-work"><a class="heading-anchor" href="#async-work">Async work</a></h3>
<pre class="mermaid">sequenceDiagram
    participant A as addon (loop thread)
    participant L as libuv loop
    participant P as thread pool
    A->>A: napi_create_async_work(execute, complete, data)
    A->>L: napi_queue_async_work (uv_queue_work), active_works++
    L->>P: execute(env, data), no JavaScript allowed
    P-->>L: done
    L->>A: after_work: active_works--, then complete(env, napi_ok, data)&#x3C;br/>inside a callback frame
    A->>A: napi_delete_async_work (usually from complete)
    Note over A,L: napi_cancel_async_work before execute starts:&#x3C;br/>complete(env, napi_cancelled, data)
</pre>
<p>The item is uncounted <em>before</em> <code>complete</code> runs, so <code>complete</code> may queue the
same item again.</p>
<h3 id="thread-safe-functions"><a class="heading-anchor" href="#thread-safe-functions">Thread-safe functions</a></h3>
<p>A port of Node 22's <code>v8impl::ThreadSafeFunction</code> on libuv primitives: a mutex,
a queue (bounded when <code>max_queue_size > 0</code>, with a condition variable for
blocked producers), a <code>uv_async_t</code> that wakes the loop thread, and at most
1000 calls dispatched per wake-up so that other handles are not starved.</p>
<pre class="mermaid">stateDiagram-v2
    [*] --> Open: napi_create_threadsafe_function&#x3C;br/>(thread_count = initial_thread_count)
    Open --> Open: call queues an item, acquire increments,&#x3C;br/>release decrements thread_count
    Open --> Closing: thread_count reaches 0 and the queue is empty
    Open --> Closing: release with napi_tsfn_abort
    Open --> Closing: env teardown (internal cleanup hook)
    Closing --> Finalized: uv_close callback runs thread_finalize_cb,&#x3C;br/>then call_js_cb(env = NULL) for each queued item
    Finalized --> [*]
</pre>
<p>While closing, producers get <code>napi_closing</code>.</p>
<h2 id="loading-addons"><a class="heading-anchor" href="#loading-addons">Loading addons</a></h2>
<pre class="mermaid">sequenceDiagram
    participant R as require / embedder
    participant L as qjsnapi_load_addon
    participant D as dlopen / LoadLibrary
    participant M as addon
    R->>L: path
    L->>D: open the absolute path (the handle is never closed)
    D->>M: static constructors run
    M-->>L: napi_module_register(mod), legacy addons only
    L->>M: dlsym napi_register_module_v1
    L->>M: dlsym node_api_module_get_api_version_v1 (optional)
    L->>L: version: missing = 8, below 8 raised to 8,&#x3C;br/>above 10 = ERR_DLOPEN_FAILED
    L->>L: new env, implicit scope, exports = {}
    L->>M: init(env, exports)
    M-->>L: exports, or a replacement value
    L-->>R: new reference to the exports
</pre>
<ol>
<li><code>node_api_module_get_api_version_v1</code> (optional, default 8) gives the module
API version. A version above 10 is refused with <code>ERR_DLOPEN_FAILED</code>; one
below 8 is raised to 8, as in Node.js.</li>
<li><code>napi_register_module_v1</code> is the symbol-based entry point (what
<code>NAPI_MODULE</code> and <code>NAPI_MODULE_INIT</code> produce).</li>
<li>Otherwise, a <code>napi_module</code> registered by <code>napi_module_register()</code> from a
static constructor <strong>during</strong> <code>dlopen</code> (legacy addons). The constructor only
runs on the first <code>dlopen</code> of a file, so the record is remembered and reused
by later loads.</li>
</ol>
<p>If the initializer returns a value other than <code>exports</code>, that value replaces
the exports, as Node.js assigns it to <code>module.exports</code>.</p>
<p>Library handles are <strong>never closed</strong>: finalizers and cleanup hooks may point
into addon code until the very end of the process.</p>
<p>Static addons, linked into the embedder, use <code>qjsnapi_init_static_addon</code>,
which runs the initializer once and caches its exports by name.</p>
<h2 id="teardown"><a class="heading-anchor" href="#teardown">Teardown</a></h2>
<p><code>qjsnapi_host_destroy</code> mirrors Node's <code>Environment::RunCleanup</code> and
<code>node_napi_env__::DeleteMe</code>:</p>
<pre class="mermaid">flowchart TD
    S["qjsnapi_host_destroy"] --> A["1. every env, newest first:&#x3C;br/>can_call_into_js = false, then cleanup hooks LIFO&#x3C;br/>(user hooks, async hooks start, thread-safe functions start closing)"]
    A --> B["2. queued async work cancelled"]
    B --> C["3. uv_run(UV_RUN_ONCE) until in-flight work,&#x3C;br/>closing thread-safe functions and&#x3C;br/>started async cleanup hooks are done"]
    C --> D["4. every env, newest first: queued finalizers,&#x3C;br/>then references with a finalizer (instance data included),&#x3C;br/>then plain references"]
    D --> E["5. module cache released (exports objects)"]
    E --> F["6. every env arena released (all napi_value slots)"]
    F --> G["7. library loop handles closed (the loop too when owned),&#x3C;br/>captured builtins released, host detached from the context"]
    G --> H["embedder: JS_FreeContext, JS_FreeRuntime"]
</pre>
<ul>
<li>References with a finalizer are finalized before plain ones, because their
finalizers may delete plain references.</li>
<li>Async work items and user references the addon never deleted are freed with
the env. Node.js leaks them; here nothing can reach them after teardown, and
freeing them keeps the QuickJS leak assertion (<code>JS_FreeRuntime</code> in Debug
builds) meaningful.</li>
<li>In the executable, <code>process.exit()</code> and fatal exceptions <strong>skip</strong> this
teardown, as Node.js does: no cleanup hook or finalizer runs.</li>
</ul>
<h2 id="captured-builtins"><a class="heading-anchor" href="#captured-builtins">Captured builtins</a></h2>
<p>Some APIs have no QuickJS C equivalent and are implemented by calling a
JavaScript builtin: <code>WeakRef</code>, <code>WeakMap.prototype.get/set</code>, <code>Object.freeze</code>,
<code>Object.seal</code>, <code>Symbol</code>, <code>Symbol.for</code>, the <code>DataView</code> and <code>%TypedArray%</code>
getters, <code>Date.prototype.getTime</code>, and BigInt conversion to and from
hexadecimal. These are captured <strong>when the host is created, before any user
script runs</strong>, and stored on the host. Monkey-patching the globals later
therefore cannot change what Node-API reports, which matches V8, where these
operations do not go through JavaScript.</p>
<p>QuickJS does not export its class ID enum. The class IDs of <code>ArrayBuffer</code>,
<code>SharedArrayBuffer</code>, <code>DataView</code>, <code>Date</code> and the 12 typed arrays are found by
<strong>probing one instance of each</strong> at startup (<code>host->cid_*</code>); type checks then
compare class IDs.</p>
<h2 id="design-decisions"><a class="heading-anchor" href="#design-decisions">Design decisions</a></h2>
<table>
<thead>
<tr>
<th>Decision</th>
<th>Alternative</th>
<th>Why</th>
</tr>
</thead>
<tbody>
<tr>
<td>Addons resolve <code>napi_*</code> from the executable</td>
<td>ship a <code>libnode</code>-like shared library</td>
<td>It is how addons are built for Node.js. Prebuilt binaries work unchanged, including MSVC builds on Windows (node-gyp's delay-load hook redirects the <code>node.exe</code> imports to the running process).</td>
</tr>
<tr>
<td><code>napi_value</code> = pointer to an arena slot that owns one reference</td>
<td>box every value in a malloc'ed handle; or cast the <code>JSValue</code> itself</td>
<td>A <code>JSValue</code> is larger than a pointer on every target (a 16-byte struct on 64-bit, a NaN-boxed 64-bit value on 32-bit). The arena gives stable addresses, O(1) allocation, and scope release without per-handle bookkeeping.</td>
</tr>
<tr>
<td>Weak callbacks through a <code>WeakMap</code> of holders</td>
<td>patch QuickJS to add weak callbacks; add hidden properties to the target</td>
<td>Uses only the public API; works on frozen objects, proxies and functions; the engine stays unpatched.</td>
</tr>
<tr>
<td>Kept-objects list for weak targets</td>
<td>pure reference-counting semantics</td>
<td>Without it, objects referenced only weakly die when the creating call returns, which breaks node-addon-api (<code>Napi::Weak</code>). The list reproduces V8's "alive until the next GC" the same way ECMAScript <code>WeakRef</code> does.</td>
</tr>
<tr>
<td>Finalizers queued and run from the loop</td>
<td>run them in the QuickJS class finalizer</td>
<td>Node.js does the same; a QuickJS class finalizer runs inside the GC, where calling into the engine is unsafe.</td>
</tr>
<tr>
<td>Dedicated function class with a <code>call</code> hook</td>
<td><code>JS_NewCFunctionData</code></td>
<td>Only the <code>call</code> hook receives <code>new.target</code>, needed by <code>napi_get_new_target</code> and <code>napi_define_class</code>.</td>
</tr>
<tr>
<td>Builtins captured at startup</td>
<td>look them up on <code>globalThis</code> at each call</td>
<td>Immune to monkey-patching, like V8; no lookup per call.</td>
</tr>
<tr>
<td>libuv as the event loop</td>
<td>a custom loop</td>
<td>Addons call <code>napi_get_uv_event_loop</code> and <code>uv_*</code> directly; the semantics of async work and thread-safe functions are defined in libuv terms.</td>
</tr>
<tr>
<td>Library and executable are separate</td>
<td>a single executable</td>
<td>The library can be embedded in any QuickJS application (<a href="/projects/quickjs-napi/docs/embedding/">embedding.md</a>); the executable is one embedder among others.</td>
</tr>
<tr>
<td>Free what the addon leaked at teardown</td>
<td>leak like Node.js</td>
<td>Debug builds of QuickJS assert that every object is released at <code>JS_FreeRuntime</code>, which turns any leak in the library into a test failure.</td>
</tr>
<tr>
<td>Node.js 22 as the behavioural reference, checked by running the same JS tests under Node.js</td>
<td>follow the Node-API documentation only</td>
<td>The documentation leaves many details open (property order, error codes, edge cases); the Node.js implementation and its test suites are the contract addons actually depend on.</td>
</tr>
</tbody>
