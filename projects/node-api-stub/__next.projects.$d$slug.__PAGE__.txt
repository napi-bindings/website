<h2 id="introduction"><a class="heading-anchor" href="#introduction">Introduction</a></h2>
<p>A native addon for Node.js calls the Node-API functions (<code>napi_*</code>, <code>node_api_*</code>)
exported by the host process (<code>node</code>, <code>node.exe</code>, Electron, ...). When the addon
is built, those symbols do not exist yet, and some toolchains refuse to link:
Windows always needs an import library, macOS rejects undefined symbols by
default, and on Linux some build systems add <code>-z defs</code>.</p>
<p>This project gives CMake projects (and any other build system) everything they
need to link an addon on every platform, without Node.js installed:</p>
<ul>
<li>the official Node-API headers, vendored from
<a href="https://github.com/nodejs/node-api-headers" target="_blank" rel="noreferrer noopener">node-api-headers</a> (Node-API 10);</li>
<li>a <code>NodeApi::NodeApi</code> target that applies the right link mechanism for the
platform;</li>
<li>optional static and shared stub libraries for the cases that need them.</li>
</ul>
<h2 id="how-it-works"><a class="heading-anchor" href="#how-it-works">How it works</a></h2>
<p>The addon must always end up calling the Node-API functions of the host
process. A library with function bodies linked into the addon can be called
instead of them, so the right mechanism depends on the platform:</p>
<table>
<thead>
<tr>
<th>Platform</th>
<th>What <code>NodeApi::NodeApi</code> does</th>
</tr>
</thead>
<tbody>
<tr>
<td>Windows, MSVC / clang-cl (x64, x86, arm64)</td>
<td>links <code>node_api.lib</code>, an import library for <code>NODE.EXE</code> generated from the official <code>.def</code> file, plus <code>/DELAYLOAD:node.exe</code> and a delay-load hook so that the addon also loads in hosts with another name (Electron, a renamed <code>node.exe</code>)</td>
</tr>
<tr>
<td>Windows, MinGW / llvm-mingw</td>
<td>links <code>libnode_api.dll.a</code>, generated with <code>dlltool</code></td>
</tr>
<tr>
<td>macOS</td>
<td><code>-Wl,-U,_&#x3C;symbol></code> for each Node-API symbol: only those may stay undefined (or <code>-undefined dynamic_lookup</code>, see options)</td>
</tr>
<tr>
<td>Linux, BSD, Android (ELF)</td>
<td>nothing is linked; adds <code>-z undefs</code> so that <code>-z defs</code> does not reject the Node-API symbols</td>
</tr>
</tbody>
</table>
<p>The import libraries are generated at configure time, so the project builds
from source anywhere a C compiler is available; prebuilt archives are also
attached to each release.</p>
<blockquote>
<p><strong>Why not a stub everywhere?</strong> A stub linked into the addon is called instead
of Node-API when the linker binds the calls inside the addon: always on
Windows and macOS, and on Linux when the addon is linked with <code>-Bsymbolic</code>.
<code>go build -buildmode=c-shared</code> always passes <code>-Bsymbolic</code>, so a Go addon
linked with the static stub calls the empty functions. The tests in
<a href="https://github.com/napi-bindings/node-api-stub/blob/main/tests/CMakeLists.txt" target="_blank" rel="noreferrer noopener"><code>tests/</code></a> reproduce this case.</p>
</blockquote>

<code>all</code> and are built only if a target links them.</p>
<h2 id="stub-libraries"><a class="heading-anchor" href="#stub-libraries">Stub libraries</a></h2>
<p>The stubs are generated from <code>def/node_api.def</code>: each function prints its own
name and calls <code>abort()</code>. They must never run; if they do, the addon fails
loudly instead of carrying on with uninitialised values.</p>
<ul>
<li><strong>Static (<code>libnode_api_stub.a</code>)</strong>: for toolchains that need an archive to
link and do not accept linker options. On ELF it works only through symbol
interposition: do not use it with <code>-Bsymbolic</code>, and therefore not with Go
<code>-buildmode=c-shared</code>.</li>
<li><strong>Shared (<code>libnode_api_stub.so</code>)</strong>: correct even with <code>-Bsymbolic</code>, but the
addon records a <code>DT_NEEDED</code> entry for it: remove it after linking
(<code>patchelf --remove-needed libnode_api_stub.so addon.node</code>) or ship the
library next to the addon.</li>
<li><strong>Windows and macOS</strong>: not recommended; built only on explicit request.</li>
</ul>
<p>Other options that avoid the link problem entirely are resolving the Node-API
functions at run time (<code>dlsym(RTLD_DEFAULT, ...)</code> / <code>GetProcAddress</code>), as
<a href="https://napi.rs" target="_blank" rel="noreferrer noopener">napi-rs</a> does, or declaring them as weak references on ELF
(<code>#pragma weak napi_create_object</code>).</p>
<h2 id="building-and-testing"><a class="heading-anchor" href="#building-and-testing">Building and testing</a></h2>
<p>You need CMake 3.16 or later and a C compiler. Node.js is optional and is used
only by the tests, which load the test addons and check that their calls reach
the real Node-API.</p>
<pre class="shiki shiki-themes github-light github-dark" style="background-color:#fff;--shiki-dark-bg:#24292e;color:#24292e;--shiki-dark:#e1e4e8" tabindex="0"><code><span class="line"><span>cmake -S . -B build -DCMAKE_BUILD_TYPE=Release</span></span>
<span class="line"><span>cmake --build build --config Release</span></span>
<span class="line"><span>ctest --test-dir build -C Release --output-on-failure</span></span>
<span class="line"><span>cmake --install build --config Release --prefix ./dist</span></span></code></pre>
<p>On Windows use the Visual Studio generator (<code>-A x64</code>, <code>-A Win32</code>, <code>-A ARM64</code>)
or MinGW / llvm-mingw with <code>-G Ninja</code>.</p>
<h2 id="updating-the-node-api-headers"><a class="heading-anchor" href="#updating-the-node-api-headers">Updating the Node-API headers</a></h2>
<p><code>include/</code> and <code>def/</code> come unmodified from the
<a href="https://www.npmjs.com/package/node-api-headers" target="_blank" rel="noreferrer noopener">node-api-headers</a> npm package.
To update them (Node.js and npm are not needed):</p>
<pre class="shiki shiki-themes github-light github-dark" style="background-color:#fff;--shiki-dark-bg:#24292e;color:#24292e;--shiki-dark:#e1e4e8" tabindex="0"><code><span class="line"><span>cmake -DVERSION=1.9.0 -P scripts/update-node-api-headers.cmake</span></span></code></pre>
<h2 id="migrating-from-8x"><a class="heading-anchor" href="#migrating-from-8x">Migrating from 8.x</a></h2>
<ul>
<li>The headers moved from the repository root to <code>include/</code>; <code>node_api.c</code> is
now generated.</li>
<li>Replace the <code>node_api</code> target with <code>NodeApi::NodeApi</code>. If you really need the
old static archive, link <code>NodeApi::legacy</code> (on ELF only).</li>
<li>The static library is now called <code>libnode_api_stub.a</code>, and its functions
abort instead of returning <code>napi_ok</code>.</li>
</ul>
