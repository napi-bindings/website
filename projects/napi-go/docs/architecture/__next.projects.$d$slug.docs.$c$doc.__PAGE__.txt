19:T210a,<h1 id="how-it-works">How it works</h1>
<h2 id="layers"><a class="heading-anchor" href="#layers">Layers</a></h2>
<pre class="shiki shiki-themes github-light github-dark" style="background-color:#fff;--shiki-dark-bg:#24292e;color:#24292e;--shiki-dark:#e1e4e8" tabindex="0"><code><span class="line"><span> your addon     //napi: annotations ──napi-go gen──▶ zz_napi.go, index.js, index.d.ts</span></span>
<span class="line"><span>      │</span></span>
<span class="line"><span> Layer 2        napi.Export, FuncN/AsyncN/MethodN, NewClass, codecs (Go ⇄ JS conversions), JSFunc</span></span>
<span class="line"><span> Layer 1        napi.Env, Value, Object, Function, errors, Ref, Async, ThreadsafeFunction</span></span>
<span class="line"><span> Layer 0        sys: the Node-API C functions 1:1, C trampolines, symbol loader</span></span>
<span class="line"><span>      │</span></span>
<span class="line"><span> Node.js        Node-API (napi_*), V8, libuv</span></span></code></pre>
<p>Each layer only uses the one below. Layer 2 and Layer 1 are both in package <code>napi</code> and can be
mixed in one addon; Layer 0 (<code>sys</code>) is for raw ABI access.</p>
<h2 id="loading"><a class="heading-anchor" href="#loading">Loading</a></h2>
<p>The addon is a shared library built by <code>go build -buildmode=c-shared</code>, renamed <code>.node</code>. When
<code>require()</code> loads it:</p>
<ol>
<li>The dynamic loader runs the Go runtime initialization (the runtime starts its threads, the
<code>init</code> functions run and register the exports).</li>
<li>Node.js calls the entry point <code>napi_register_module_v1</code> (<code>sys/module.c</code>), which resolves every
Node-API function from the host process with <code>dlsym</code> or <code>GetProcAddress</code>. The library has no
undefined symbols and no import library: it builds without Node.js installed, and a function
missing from the running Node.js is reported, not a crash at load time.</li>
<li>For every env that loads the addon (the main thread, each worker thread), the registered exports
are created.</li>
</ol>
<p>The declared Node-API version is 8 by default, 9 or 10 with the build tags <code>napi_go_v9</code> and
<code>napi_go_v10</code> (<a href="/projects/napi-go/docs/sys/#declared-node-api-version">sys</a>).</p>
<h2 id="a-call"><a class="heading-anchor" href="#a-call">A call</a></h2>
<pre class="shiki shiki-themes github-light github-dark" style="background-color:#fff;--shiki-dark-bg:#24292e;color:#24292e;--shiki-dark:#e1e4e8" tabindex="0"><code><span class="line"><span>JS add(1, 2)</span></span>
<span class="line"><span> └▶ V8 ─▶ Node-API ─▶ C trampoline (sys/typed.c): reads 1 and 2 as doubles</span></span>
<span class="line"><span>                       └▶ one cgo callback into Go: the Go function, by its ID in a table</span></span>
<span class="line"><span>                       ◀─ result 3 as a double</span></span>
<span class="line"><span>                      C creates the JS number</span></span></code></pre>
<ul>
<li><strong>One crossing per call.</strong> Numbers, booleans and strings up to about 500 bytes are converted in
C, before and after the single crossing into Go, as is the <code>this</code> of methods. Other types are
converted in Go by codecs: one per Go type, built once with reflection and cached, working on
<code>unsafe</code> pointers at run time, with no Go allocation for primitives, <code>[]byte</code>, napi values and
class pointers.</li>
<li><strong>The crossing is the floor.</strong> Node.js calls on its own thread, which is not a Go thread; entering
Go costs about 100 ns on Linux (about 1 µs on Windows, where the Go runtime lacks an
optimization for threads created outside Go). A call from Rust or C++ costs a few nanoseconds.
The <a href="/projects/napi-go/docs/bench/">benchmarks</a> compare the three.</li>
<li><strong>Errors</strong> returned by Go are thrown as JS exceptions on the way out; panics are recovered and
thrown as <code>GO_PANIC</code>.</li>
</ul>
<h2 id="threads"><a class="heading-anchor" href="#threads">Threads</a></h2>
<p>V8 runs JavaScript on one thread per env, and every Node-API call must be made on it. Goroutines
run on the threads of the Go scheduler, so they never call Node-API: they hand work to the JS
thread.</p>
<ul>
<li><strong>One dispatcher per env.</strong> Each env has one threadsafe function (unref'd: it does not keep
Node.js alive) and a Go queue of closures. A goroutine appends to the queue, and wakes the JS
thread only if the queue was empty: a thousand goroutines finishing together cost one wake-up.</li>
<li><strong>Async functions</strong> (<code>AsyncN</code>, <code>Env.Async</code>) convert the arguments on the JS thread, run the Go
function in a goroutine, and settle the Promise through the dispatcher. Node.js stays alive while
any is pending.</li>
<li><strong>ThreadsafeFunction[T]</strong> and <strong>JSFunc[A, R]</strong> let goroutines call JS functions (with the result
converted back, for <code>JSFunc</code>).</li>
<li><strong>Env context.</strong> <code>Env.Context()</code> is canceled when the env is destroyed (worker terminated,
process exiting); pending Promises are dropped and threadsafe functions return <code>ErrClosing</code>.</li>
</ul>
<h2 id="memory"><a class="heading-anchor" href="#memory">Memory</a></h2>
<p>Two garbage collectors manage the objects of an addon: V8 for JS values, Go for Go values. cgo
forbids handing Go pointers to C for C to keep, so:</p>
<ul>
<li><strong>Go values given to JS are found by ID.</strong> Callbacks, class instances, externals and finalizers
live in Go tables; Node-API receives an integer. When V8 collects the JS object, its finalizer
frees the ID and the Go value becomes collectable. Reads of the tables are lock-free.</li>
<li><strong>JS values held by Go are references</strong> (<code>Value.NewRef</code>, napi_ref), released explicitly or from
a goroutine with <code>Ref.DeleteLater</code>. A plain <code>napi.Value</code> is valid only during the call.</li>
<li><strong>Buffers.</strong> A <code>[]byte</code> parameter is a view of V8 memory, valid during the call. A returned
<code>[]byte</code> is copied into a new Buffer. <code>NewExternalBuffer</code> hands Go memory to JS without a copy,
pinned with <code>runtime.Pinner</code> until V8 releases it.</li>
<li><strong>Class instances.</strong> A JS instance holds the ID of its <code>*T</code>. In an env, the same <code>*T</code> always maps
to the same JS object, and <code>Finalize</code> runs when the last instance is collected.</li>
</ul>
<h2 id="signals"><a class="heading-anchor" href="#signals">Signals</a></h2>
<p>The Go runtime and Node.js both install signal handlers in one process. Go requires every handler
to run on the alternate signal stack (<code>SA_ONSTACK</code>): a signal can arrive on a Go thread, whose
stack is small. Handlers that Node.js and libuv install after the addon has loaded
(<code>process.on('SIGINT')</code>, child processes) lack the flag; on Linux, <code>sys/onstack.c</code> adds it to
them by intercepting <code>sigaction</code> in the process. On macOS, the Go runtime reinstalls the handlers
that are already there to add <code>SA_ONSTACK</code>, and the macOS kernel does not report <code>SA_RESETHAND</code>,
so the flag is lost on the handler that Node.js uses to exit on SIGINT and SIGTERM; the handler
then calls itself forever. <code>sys/sigfix.c</code> restores the flag. The e2e
tests check WebAssembly traps, child processes, SIGINT and SIGTERM with the addon loaded and Go
busy.</p>
