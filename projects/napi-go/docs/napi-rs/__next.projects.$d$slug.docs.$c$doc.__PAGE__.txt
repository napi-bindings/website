19:T1944,<h1 id="coming-from-napi-rs">Coming from napi-rs</h1>
<p>napi-go follows the design of napi-rs: annotated declarations, conversions from the types of the
language, TypeScript declarations, one npm package per platform. The table maps the napi-rs
features to napi-go.</p>

<h2 id="differences"><a class="heading-anchor" href="#differences">Differences</a></h2>
<ul>
<li><strong>Call overhead.</strong> A call into Go crosses from C into the Go runtime (about 100 ns on Linux,
about 1 µs on Windows), where napi-rs calls Rust directly. Conversions of numbers and short
strings happen in C in the same crossing. Bulk Promises are cheaper than in napi-rs. See the
<a href="/projects/napi-go/docs/bench/">benchmarks</a>.</li>
<li><strong>Binary size.</strong> The Go runtime is part of every addon: a small addon is about 2.5 MB stripped,
against well under 1 MB for napi-rs.</li>
<li><strong>Platforms.</strong> No musl (Alpine): Go cannot build shared libraries that load with musl. On macOS
x64 only one Go addon can be loaded per process. No WebAssembly target. See
<a href="/projects/napi-go/docs/platforms/">platforms</a>.</li>
<li><strong>Two garbage collectors.</strong> Go values referenced from JS live until V8 collects the JS object;
a <code>[]byte</code> parameter must not be kept after the call.</li>
<li><strong>Concurrency.</strong> Goroutines replace the tokio runtime and the libuv thread pool; there is no
runtime to configure.</li>
