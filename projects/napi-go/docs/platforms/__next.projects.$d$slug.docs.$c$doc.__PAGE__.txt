<ul>
<li><strong>Go</strong> 1.24 or later (the <code>tool</code> directive of <code>go.mod</code> used by the template needs 1.24).</li>
<li><strong>Node.js</strong> 22 or later is tested. Addons declare Node-API 8 by default (Node.js 12.22 and later
provide it); the build tags <code>napi_go_v9</code> and <code>napi_go_v10</code> declare 9 and 10 for their functions
and behaviors.</li>
<li><strong>Worker threads</strong>: supported; each worker loads the addon in its own env.</li>
<li><strong>Electron</strong>: not tested. Where external buffers are not allowed (the V8 sandbox), napi-go copies
instead.</li>
</ul>
<h2 id="known-limitations"><a class="heading-anchor" href="#known-limitations">Known limitations</a></h2>
<ul>
<li><strong>musl (Alpine Linux) is not supported.</strong> No Go release builds a shared library that loads with
musl: <code>dlopen</code> rejects the initial-exec TLS of the Go runtime (golang/go#71953; the Go change
CL 696635 fixes it and is tracked in CI). The loader in <code>index.js</code> explains it on musl.</li>
<li><strong>macOS x64: one Go addon per process.</strong> On darwin/amd64 every Go runtime uses the same TLS slot
for the current goroutine (golang/go#23617). A second napi-go addon (or any other Go c-shared
library) is rejected with <code>ERR_NAPI_GO_FOREIGN_RUNTIME</code> instead of corrupting memory. macOS arm64,
Linux and Windows load any number of Go addons.</li>
<li><strong>Windows: a call costs about 1 µs</strong>, against about 100 ns on Linux: the Go runtime lacks an
optimization for threads created outside Go on Windows (<code>x_cgo_bindm</code>).</li>
<li><strong>Binary size</strong>: the Go runtime is in every addon, about 2.5 MB for a small one (stripped).</li>
<li><strong>Not wrapped yet</strong>: async hooks (<code>napi_async_init</code>, <code>napi_make_callback</code>), the libuv thread pool
(<code>napi_async_work</code>) and SharedArrayBuffer are only in <code>sys</code>; asynchronous class methods are not
supported by Layer 2 (call <code>Env.Async</code> in a method). See the
<a href="/projects/napi-go/docs/napi/#current-limitations">current limitations</a>.</li>
</ul>
<h2 id="troubleshooting"><a class="heading-anchor" href="#troubleshooting">Troubleshooting</a></h2>
<table>
<thead>
<tr>
<th>Symptom</th>
<th>Cause and fix</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>cannot load the native addon … for linux-x64-musl</code></td>
<td>musl is not supported: use a glibc-based image (Debian, Ubuntu, Red Hat, <code>node:*-slim</code>)</td>
</tr>
<tr>
<td><code>cannot load the native addon … package not installed</code></td>
<td>the platform package was not installed: <code>npm install</code> with optional dependencies enabled (not <code>--omit=optional</code>), on the same platform as the one that runs the code</td>
</tr>
<tr>
<td><code>GLIBC_2.xx not found</code></td>
<td>the binary was built against a newer glibc: build with zig (<code>napi-go build -release</code>, the default when zig is installed)</td>
</tr>
<tr>
<td><code>ERR_NAPI_GO_FOREIGN_RUNTIME</code></td>
<td>macOS x64: a second Go addon in the process (see above)</td>
</tr>
<tr>
<td><code>ERR_NAPI_GO_MISSING_FUNCTIONS</code></td>
<td>the Node.js version lacks Node-API functions of the declared version: drop the <code>napi_go_v9</code>/<code>napi_go_v10</code> tag or update Node.js</td>
</tr>
<tr>
<td><code>cross-compiling for … needs zig</code></td>
<td>install <a href="https://ziglang.org/download/" target="_blank" rel="noreferrer noopener">zig</a> or build on that platform</td>
</tr>
<tr>
<td><code>cgo: C compiler "gcc" not found</code> (Windows)</td>
<td>install MinGW gcc, or use <code>napi-go build -zig always</code> with zig</td>
</tr>
<tr>
<td>a TypeError <code>ERR_INVALID_ARG_TYPE</code> from an addon function</td>
<td>a JS argument of the wrong type: the message names the argument and the path inside it</td>
</tr>
<tr>
<td>a <code>GO_PANIC</code> error</td>
<td>a panic in the Go function; its message is the panic value</td>
</tr>
</tbody>
</table>
