<h2 id="design-choices"><a class="heading-anchor" href="#design-choices">Design Choices</a></h2>
<p><strong>Runtime-resolved symbols.</strong> No import library and no undefined symbols at link time: the
<code>.node</code> binary does not link against <code>node.exe</code>/<code>node</code> and compiles with <code>go build</code>/<code>go test</code>
without Node installed. Calling a function missing from the host Node process returns
<code>StatusUnavailable</code>; <code>Available(Fn…)</code> checks availability in advance. Functions up to the
declared Node-API version are required: if any are missing, module loading fails with
<code>ERR_NAPI_GO_MISSING_FUNCTIONS</code>.</p>
<p><strong>By-value outputs.</strong> cgo avoids moving a Go pointer passed to C onto the heap only if the
function has <em>both</em> <code>noescape</code> <em>and</em> <code>nocallback</code>. Functions that may execute JS (getters,
Proxies, <code>call_function</code>, ...) cannot be marked <code>nocallback</code>, so <code>&#x26;result</code> would escape to the
heap on every call. Therefore, each C wrapper returns outputs by value in a struct: the Go
signature stays 1:1 (pointers, <code>nil</code> = <code>NULL</code>), but no Go output pointer crosses cgo.
Measured result in e2e tests: <strong>0 allocations per call</strong>, even for <code>GetNamedProperty</code>.</p>
<p><strong>Opaque data as <code>uintptr</code>.</strong> <code>void*</code> values retained by Node-API (data, hint, context, ...) are
exposed as <code>uintptr</code>: cgo rules forbid handing Go pointers to C for long-term storage, and the
type makes this explicit.</p>
<p><strong><code>noescape</code> / <code>nocallback</code>.</strong> Still useful for input buffers (strings, argument arrays).
<code>nocallback</code> is applied only to functions that never execute JS; if one were to re-enter Go, the
Go runtime would terminate the process with an explicit fatal error. With <code>napi_go_experimental</code>,
finalizers can run synchronously during V8 GC (verified: all run inside <code>gc()</code>), so
<code>nocallback</code> is restricted to functions that never allocate on the V8 heap. The cost is
measurable: stack buffers passed to e.g. <code>GetValueStringUTF8</code> escape to the heap (1 allocation
per iteration in test benchmarks, vs. 0 with versions 8–10).</p>

declared version (and with it Node's runtime behavior, e.g. synchronous finalizers).
<code>napi_go_test_version_mismatch</code> declares a version no Node.js supports and is used solely to
test module rejection (<code>tests/nodesuite</code>, test_module_version_mismatch).</p>
<p>An addon that does not register a <code>ModuleInitHandler</code> fails to load: <code>require()</code> throws
<code>ERR_NAPI_GO_NO_HANDLER</code> with Node.js's standard message for a module without an entry point
("Module has no declared entry point.").</p>
<h2 id="known-limitations"><a class="heading-anchor" href="#known-limitations">Known Limitations</a></h2>
<ul>
<li><strong>macOS x64: one Go addon per process.</strong> On darwin/amd64 all Go runtimes store <code>g</code> in the fixed
TLS slot <code>0x30(GS)</code> (golang/go#23617). <code>guard.c</code> rejects entry into a second Go runtime with
<code>ERR_NAPI_GO_FOREIGN_RUNTIME</code> instead of corrupting memory. However, the rejected runtime has
already initialized and its signal handlers remain installed; this still needs further investigation.</li>
<li><strong>musl/Alpine</strong> is unsupported: Go releases (≤ 1.27) cannot load <code>c-shared</code> libraries on musl.</li>
<li><strong>Windows</strong>: each JS → Go entry costs ~1 µs (missing <code>x_cgo_bindm</code> in the Go runtime).</li>
</ul>
