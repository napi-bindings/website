19:T2d4b,<h1 id="packaging-marmotta">Packaging Marmotta</h1>
<p>This directory contains the package-manager recipes for Marmotta. They are rendered from the
release executables and the <code>SHA256SUMS</code> asset that the <code>Release binaries</code> workflow publishes.</p>

<h2 id="building-native-linux-packages"><a class="heading-anchor" href="#building-native-linux-packages">Building native Linux packages</a></h2>
<p>The <code>.deb</code>, <code>.rpm</code>, <code>.apk</code>, and Arch Linux packages are built with
<a href="https://nfpm.goreleaser.com/" target="_blank" rel="noreferrer noopener">nfpm</a>:</p>
<pre class="shiki shiki-themes github-light github-dark" style="background-color:#fff;--shiki-dark-bg:#24292e;color:#24292e;--shiki-dark:#e1e4e8" tabindex="0"><code><span class="line"><span style="color:#6A737D;--shiki-dark:#6A737D"># https://github.com/goreleaser/nfpm/releases</span></span>
<span class="line"><span style="color:#6F42C1;--shiki-dark:#B392F0">node</span><span style="color:#032F62;--shiki-dark:#9ECBFF"> scripts/packages.mjs</span><span style="color:#005CC5;--shiki-dark:#79B8FF"> --artifacts</span><span style="color:#032F62;--shiki-dark:#9ECBFF"> dist</span><span style="color:#005CC5;--shiki-dark:#79B8FF"> --out</span><span style="color:#032F62;--shiki-dark:#9ECBFF"> packaging/out</span><span style="color:#005CC5;--shiki-dark:#79B8FF"> --build</span></span></code></pre>
<p>The script verifies every package after building it: metadata (name, version, architecture) and
the installed files are read back from each package. Verification needs <code>tar</code> and <code>ar</code>; it uses
<code>rpm</code> or <code>bsdtar</code> to list RPM contents, and <code>bsdtar</code> (or <code>tar</code> with zstd support) for Arch Linux
packages. When <code>--sums</code> and <code>--build</code> are combined, the executables in <code>--artifacts</code> are checked
against <code>SHA256SUMS</code> before any package is built, so a stale <code>dist/</code> cannot produce packages that
disagree with the published checksums.</p>
<p>Only plain <code>MAJOR.MINOR.PATCH</code> versions are supported: nfpm rewrites pre-release and build
metadata differently per package format, which would make the generated spec and APKBUILD invalid.</p>
<p>The recipes reference <code>LICENSE</code> at tag <code>v&#x3C;version></code>. When that tag exists locally, the renderer
hashes the committed blob from the tag (<code>git show v&#x3C;version>:LICENSE</code>); otherwise it uses the
working tree, so render an older version from a checkout of that tag. The Alpine recipe also needs
the release executables in <code>--artifacts</code> to compute the SHA-512 checksums that aports requires.</p>
<p>The <code>.apk</code> packages built by nfpm are unsigned. Add <code>--allow-untrusted</code> when installing them
directly, or sign them for a repository.</p>
<p>The release workflow installs a pinned nfpm version through
<code>.github/actions/setup-packaging</code>, runs <code>node --test test/packaging.test.js</code> with that nfpm, and
attaches the results to the GitHub release together with <code>SHA256SUMS.packages</code> and
<code>marmotta-vX.Y.Z-packaging.tar.gz</code> (the rendered recipes and their manifest). Packaging runs in a
separate job after the binary release, so a packaging failure never blocks the executables.</p>
<p>A second CI job renders the recipes from fixture checksums and runs each one through its consumer:
<code>ruby -c</code> for the formula, <code>abuild validate</code> for the APKBUILD, <code>makepkg --printsrcinfo</code> for the
PKGBUILD, <code>rpmspec -P</code> and <code>rpmspec -q</code> for the spec, and <code>nix-instantiate --parse</code> for the Nix
expression. This catches recipe syntax that filling in the placeholders alone would not.</p>

<p>All packages install a <code>marmotta</code> executable. Zig is downloaded on first use unless a compatible
Zig is already on <code>PATH</code>, <code>MARMOTTA_ZIG_DIR</code> is set, or a release pins <code>zigVersion</code>. Package
maintainers may want to add Zig as an optional/recommended dependency so first use works offline.</p>
<h2 id="publishing-checklist"><a class="heading-anchor" href="#publishing-checklist">Publishing checklist</a></h2>
<p>Packages are attached to every GitHub release so users can install them directly. Publishing to
the package-manager repositories themselves still happens from those repositories:</p>
<ol>
<li><strong>Homebrew</strong>: copy <code>homebrew/marmotta.rb</code> into the <code>napi-bindings/homebrew-tap</code> repository (or
submit it to <code>homebrew-core</code>), update the tap, and run <code>brew audit --strict</code>.</li>
<li><strong>AUR</strong>: push <code>aur/PKGBUILD</code> to the <code>marmotta-bin</code> AUR repository and run
<code>makepkg --printsrcinfo > .SRCINFO</code> before committing.</li>
<li><strong>Debian/Ubuntu</strong>: upload the <code>.deb</code> files to an APT repository with <code>dpkg-scanpackages</code>, or
submit the package to Debian/Ubuntu. Generate <code>Packages</code>/<code>Release</code> metadata for the repository.</li>
<li><strong>Fedora/RHEL</strong>: submit <code>rpm/marmotta.spec</code> through dist-git or build it in COPR. Upload the
source asset to the lookaside cache.</li>
<li><strong>Alpine</strong>: submit <code>alpine/APKBUILD</code> to <code>alpinelinux/aports</code> (or build it with <code>abuild</code>).</li>
<li><strong>Nixpkgs</strong>: add <code>nix/default.nix</code> to <code>pkgs/by-name/ma/marmotta/package.nix</code>, or expose it as a
flake/overlay first.</li>
<li><strong>Scoop</strong>: copy <code>scoop/marmotta.json</code> to a Scoop bucket.</li>
<li><strong>winget</strong>: submit the three files under <code>winget/</code> to <code>microsoft/winget-pkgs</code> with
<code>wingetcreate submit</code>.</li>
</ol>
<p>The recipes are version-specific, so regenerate them from the new <code>SHA256SUMS</code> for every release.
